# Contributing to Biref Explorer

Thanks for taking the time to contribute. This document covers the
ground rules so your pull request lands smoothly.

## Getting set up

```bash
git clone https://github.com/joelorzet/biref-explorer.git
cd biref-explorer
npm install
npm run dev
```

The dev server runs on [http://localhost:5173](http://localhost:5173).
You will need a reachable Postgres database to actually use the app,
but the build and test commands run fine without one.

## Before you push

Run the full verification pipeline locally. CI runs the same thing.

```bash
npm run verify    # typecheck + biome check
npm run build     # next build
```

If either fails, fix it before opening a pull request.

## House rules

These are the patterns the codebase relies on. Stick to them and your
change will read like the rest of the app.

### 1. Components render. Hooks think.

React components in `src/components/` should be presentational. If
your change introduces `useState`, `useEffect`, `useMemo`, or an
async handler inside a component, move that logic into a hook under
`src/hooks/` instead.

Before writing a new hook, check the shared primitives:
`useAsyncAction`, `useAsyncResource`, `useArrayState`, `useToggleSet`,
`useTextFilter`, `useGlobalEnter`, `useOutsideClick`,
`useAnchoredRect`. Compose these rather than reinventing them.

### 2. Keep files small

Every source file should stay under about 200 lines. When a component
crosses that line, split it into smaller named children in their own
files. Prefer many small files over a few large ones.

### 3. Services live in `src/lib/services/`

Anything that talks to the network, the scanner SDK, or the toast
library is a class in `src/lib/services/`. Dependencies come through
the constructor. The `src/lib/container/` files wire the singletons
together. Hooks and route handlers pull what they need from the
container, never instantiate services directly.

### 4. Add drivers through the strategy pattern

New database drivers go under
`src/lib/services/biref/drivers/`. Implement `DriverStrategy`,
register your implementation in `buildDefaultDriverRegistry`, and
add the driver id to `shared/api.ts`. You should not need to touch
`SessionStore`, the API routes, or the UI components.

### 5. Type every request and response

If you add a new API route, declare the request and response shapes
in `shared/api.ts` and import them from both sides. The wire is
typed on purpose.

### 6. Write comments that explain _why_

Do not write comments that restate what the code does. Write them
only when there is a non-obvious constraint, a workaround, or a
surprising behavior that future-you will want to know about.

### 7. Plain prose only

No em-dashes (`—`) or en-dashes (`–`) in code, comments, UI copy,
or commit messages. Use colons, parentheses, or periods instead.

### 8. No icons from emoji

Use SVG icons from `@untitled-ui/icons-react` via the
`src/components/icons.tsx` re-export. If you need a new icon, add it
to that file.

## Commit messages

Short, imperative, and describe the _why_ in the body if the change
is not obvious from the title.

```
Fix relation picker overflowing the result panel

The include cards share a stacking context with the query result
panel, so the absolute dropdown was being covered whenever the
result expanded. Switched to a portaled popover anchored to the
trigger's getBoundingClientRect.
```

Do not add AI attribution, "Co-Authored-By" lines, or "Generated by"
notes.

## Pull requests

- Keep the PR focused. One change per PR is easier to review.
- Describe _what_ and _why_ in the body. Screenshots help for UI
  changes.
- Make sure `npm run verify` and `npm run build` are green.
- Update the README if you add a visible feature.

## Reporting issues

Open a GitHub issue with:

- What you expected to happen
- What actually happened
- Exact steps to reproduce
- Your Node version, Postgres version, and browser if the bug is
  visual

Thanks again. Every bit of feedback and every pull request helps.
